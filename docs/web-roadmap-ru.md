# Путь к интерактивному веб-интерфейсу

Этот документ описывает инженерный план, а не каноническую семантику Onto4.
Цель — сделать веб-интерфейс, в котором пользователь может подключить
собственную языковую модель и пройти полный цикл уточнения и оценки, не
превращая модель в источник вердиктов `T/F/U/C`.

## Пользовательский сценарий

Пользователь открывает веб-интерфейс, выбирает профиль провайдера и задаёт
вопрос. Если исходная формулировка допускает несколько трактовок, интерфейс
показывает вопрос на уточнение. После ответа система явно запускает новую
формализацию и оценку для следующего снимка интерпретации.

Результат должен показывать не только итоговый вердикт, но и основание, на
котором он получен:

```text
вопрос пользователя
    ↓
пространство интерпретаций
    ↓
уточнение, если оно необходимо
    ↓
кандидаты формализации
    ↓
детерминированная оценка Onto4
    ↓
T / F / U / C, свидетельства и альтернативные трактовки
```

Это не обычный чат, где языковая модель сразу пишет ответ. Интерпретация,
формализация, переход после уточнения, оценка и вердикт остаются разными
операциями.

## Исходная точка

В репозитории уже есть детерминированное ядро, границы
`InterpretationProvider` и `FormalizationProvider`, типизированный механизм
уточнений и `ReasoningSession` с явной повторной оценкой. Модельные адаптеры,
HTTP API и веб-интерфейс ещё не входят в готовый пользовательский путь. Этапы
ниже добавляют их по одному, чтобы ошибки транспорта и модели не маскировали
ошибки оркестрации.

## Подключение собственной модели

Первый поддерживаемый протокол — OpenAI-compatible API. Минимальный профиль
провайдера содержит:

```text
name
protocol = openai-compatible
base_url
model
authentication = none | bearer
```

Поле аутентификации не называется «паролем»: на первом этапе поддерживаются
отсутствие аутентификации и Bearer-токен. Произвольные заголовки и специальные API
отдельных поставщиков можно добавить позже, когда появятся подтверждённые
сценарии, которые нельзя выразить через первый контракт.

Один такой профиль может указывать на локальную или удалённую точку доступа:

```text
http://127.0.0.1:8080/v1
https://llm.example.org/v1
```

Идентичность конкретной модели не входит в семантику Onto4. Точка доступа,
протокол, имя модели и реквизиты доступа — инфраструктурная конфигурация,
которая подключается к существующим границам `InterpretationProvider` и
`FormalizationProvider`.

В первом интерфейсе один профиль может обслуживать обе роли. Раздельный выбор
моделей для интерпретации, формализации и последующего объяснения результата
появится в дополнительных настройках, не меняя контракт ядра.

## Граница полномочий модели

Языковая модель может предложить:

- `InterpretationSpace`;
- `FormalizationCandidate[]`;
- человекочитаемое объяснение уже полученного результата.

Она не выдаёт авторитетный `T/F/U/C`. Кандидаты проходят проверку схемы и
происхождения данных, после чего вердикт вычисляет детерминированное ядро:

```text
Provider profile
    ↓
InterpretationProvider
    ↓
InterpretationSpace
    ↓
FormalizationProvider
    ↓
FormalizationCandidate[]
    ↓
Onto4 core
    ↓
ReasoningSession
    ↓
clarification или T / F / U / C
```

Ни провайдер, ни веб-интерфейс не получают права подменять решение ядра.

## Два режима соединения

### Onto4 HTTP runtime

Основной путь к полному сквозному сценарию сохраняет Python-ядро:

```text
Browser
    ↓
Onto4 HTTP API
    ↓
Python Onto4
    ↓
пользовательская точка доступа к языковой модели
```

Адрес модели и реквизиты доступа передаются выбранной пользователем среде
исполнения Onto4 для текущей сессии. Первый рабочий вариант предполагает
локальное или самостоятельно размещённое исполнение: пользователь явно доверяет ему свой
токен. Публичный общий сервер не должен принимать чужие реквизиты без отдельной
модели доверия, защиты и понятной политики хранения.

### Прямое соединение из браузера

Статическая страница может обращаться к пользовательской точке доступа без
нашего сервера:

```text
GitHub Pages
    ↓
браузер пользователя
    ↓
пользовательская точка доступа к языковой модели
```

Этот режим исследуется отдельно. Он требует:

- разрешённых CORS-запросов;
- совместимости браузера с обращением от публичной HTTPS-страницы к
  `localhost` или частной сети;
- способа исполнить детерминированное ядро Onto4 в браузере, а не заменить его
  ответом модели.

Поэтому прямое соединение подходит для эксперимента с транспортом и
пользовательскими профилями, но не считается полным циклом Onto4, пока ядро
не доступно в браузерной среде исполнения.

## Работа с реквизитами доступа

Статический интерфейс не получает секрет из GitHub Actions или секретов
репозитория. Любой секрет, встроенный в HTML или JavaScript при сборке, становится
доступен посетителю сайта.

По умолчанию:

- `base_url`, протокол и имя модели можно сохранить локально как профиль;
- Bearer-токен живёт только в памяти текущей вкладки;
- закрытие вкладки удаляет токен;
- сохранение токена требует отдельного явного согласия и не входит в первый
  выпуск;
- журналы и сообщения об ошибках не должны содержать реквизиты доступа.

Интерфейс явно сообщает, куда отправляется токен. В режиме прямого соединения он
уходит только к указанной точке доступа. В режиме HTTP-среды Onto4 он
передаётся выбранной среде исполнения, поэтому граница доверия должна быть видна до
начала сессии.

## Последовательность реализации и экспериментов

### 1. Контракт OpenAI-compatible провайдера

- ввести типизированный `ProviderProfile`;
- поддержать способы аутентификации `none` и `bearer`;
- реализовать проверку соединения;
- не сохранять реквизиты доступа в тестовых данных, журнале или сообщении об ошибке;
- зафиксировать тайм-аут запроса и ограничения размера ответа.

### 2. Интерпретация и формализация с помощью модели

- реализовать отдельные OpenAI-compatible adapters для
  `InterpretationProvider` и `FormalizationProvider`;
- требовать структурированный ответ и отвергать его при нарушении контракта;
- сохранить происхождение `conceptual_depth`, readings, assumptions и candidates;
- не подключать модель к детерминированному вычислению `T/F/U/C`.

### 3. Реальный интерактивный CLI-сценарий

- добавить `onto4 ask` поверх тех же профилей и границ провайдеров;
- прогнать полный путь от естественного языка через реальную модель к
  `InterpretationSpace`, кандидатам и детерминированной оценке;
- показать уточнение, применить ответ к зафиксированному ожидающему вопросу и
  отдельно запустить повторную оценку;
- собрать набор реальных вопросов и сбоев до проектирования HTTP API;
- не превращать CLI в отдельную реализацию контракта оркестрации.

Этот этап служит дешёвой проверкой всего сквозного сценария. Если модель
нарушает схему, теряет происхождение данных или систематически создаёт непригодные
формализации, это должно стать видно до появления дополнительного сетевого и
пользовательского слоя.

### 4. Минимальный Onto4 HTTP API

- открыть операции создания `ReasoningSession`, ответа на ожидающее уточнение
  и явной повторной оценки;
- сохранить связь существующего `ReasoningSession` с точным снимком;
- не запускать повторную оценку автоматически после ответа;
- передавать профиль провайдера на уровне сессии, не включая его в семантический
  контекст Onto4.

### 5. Минимальный статический веб-интерфейс

- добавить `apps/onto4-web`;
- дать пользователю указать среду исполнения Onto4, `base_url` языковой модели, её имя и способ
  аутентификации;
- добавить `Test connection`;
- хранить профиль без реквизитов доступа;
- показать явные ошибки CORS, mixed content, тайм-аута и недоступности точки доступа.

### 6. Интерактивный `ReasoningSession`

- показать ожидающее уточнение и допустимые варианты ответа;
- после ответа отобразить переход к следующему снимку;
- запускать повторную оценку отдельным явным действием процесса;
- отображать landscape, verdict, `Evidence4` и альтернативные трактовки, не
  смешивая эти уровни.

### 7. Эксперимент с прямым соединением из браузера

- проверить OpenAI-compatible точки доступа с CORS на `localhost` и удалённых
  HTTPS-адресах;
- выбрать способ исполнения Python-ядра в браузере или предоставить
-  эквивалентную проверяемую среду исполнения;
- сравнить поведение с HTTP API на одних fixture-сценариях;
- публиковать этот режим как поддерживаемый только после проверки полного
  цикла, а не одного вызова модели.

### 8. Расширение провайдеров и эксплуатационная защита

- добавлять произвольные заголовки и специальные протоколы по реальным сценариям;
- разрешить разные профили для интерпретации, формализации и подготовки объяснения;
- для публичной среды исполнения ввести ограничения частоты запросов, лимиты ввода и вывода,
  тайм-аут, список разрешённых моделей, дневной бюджет и защиту от автоматического
  злоупотребления;
- отдельно решить хранение и версионирование сессий, не связывая их с первым интерфейсом.

## Критерий первого полноценного выпуска

Первый полноценный веб-срез готов, когда пользователь может подключить свою
OpenAI-compatible модель, задать естественно-языковой вопрос, ответить на
зафиксированное уточнение и получить результат нового явного прохода оценки.
При этом реквизиты доступа не сохраняются по умолчанию, модель не выдаёт вердикт от
имени Onto4, а каждый переход остаётся связан с точным снимком интерпретации.
